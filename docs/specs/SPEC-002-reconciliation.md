# SPEC-002: Asset Reconciliation

`Decide(observation, candidates, policy)` chooses an asset key and returns a merge plan. The Go and GLib C APIs use the
same algorithm. Applications supply eligible active identifiers and candidates, enforce access and scanner/network
boundaries, generate keys, retain evidence, and apply results atomically. The library does not store results, read
history, or use the wall clock.

## Inputs and results

- `Observation`: incoming `Identifiers`.
- `Candidate`: an existing `AssetKey`, its `Identifiers`, and optional `LastSeen`. Supply one candidate per key.
- `Decision`: the action, matching stage, selected key/index, and merge indices.

| Action   | `NeedsNewKey` | `SelectedKey` / `SelectedIndex` | Merge destination                    |
|----------|---------------|---------------------------------|--------------------------------------|
| `CREATE` | true          | Empty / nil                     | New key generated by the application |
| `REUSE`  | false         | Existing key / its input index  | Selected candidate's key             |

`Stage` is `STRONG`, `CONTINUITY`, or `FUZZY`. Only strong-stage decisions can have `MergeIndices`: original candidate
positions to move to the destination key. Preserve candidate ordering until applying the result. An empty merge list
means no moves. Invalid input returns an error and a zero decision. Inputs are not changed or retained; returned data is
independent. Concurrent calls may share immutable inputs. See [`reconciliation.go`](../../identity/reconciliation.go)
for the Go types.

## Policy

`MatchPolicy` contains `StrongOrder`, `Continuity`, and ordered fuzzy members (`Type`, `Weight`).
`GreenboneMatchPolicy()` uses this strong priority, highest first:

Cloud identifier → Greenbone ID → Machine ID → BIOS UUID.

Default continuity types are Agent ID, SSH host key, and TLS public-key hash. Their order does not rank continuity
matches.

Default fuzzy members, in score accumulation order, are MAC (1.0), hostname (0.4), IP (0.4), and FQDN (0.4). Hostname
and FQDN are distinct types; compare their full normalized names.

Callers may reorder, reclassify, or omit supported types. An empty list disables that stage; it does not restore
defaults. An empty policy is valid. Reject unknown types, duplicate members, and types in more than one stage. Weights
must be positive, finite, and representable as positive finite float32. Defaults and clones own their slices.

## Strong matching

Normalize all views once using [SPEC-001B](SPEC-001B-normalization.md); omit placeholders and duplicates as evidence. A
raw `x509:` certificate counts only if its subject CN or a DNS SAN equals a hostname or FQDN in the same view:
ASCII names, case-insensitive, final dot ignored, no wildcards. Convert admitted certificates to SPKI hashes; supplied
`spki-sha256:` hashes remain eligible. `EvaluateStrongPriority` and `MatchingIdentifiers` apply the same admission
rules.

1. Compare the highest-priority strong type present in **both** views. Missing types are skipped. A conflict at this
   shared type excludes the candidate from every stage; a lower match cannot override it. Default strong types match any
   equal canonical value.
2. Prefer the highest-priority shared match, then newest present `LastSeen`, then smallest asset key by byte order.
   Missing times rank last; compare UTC instants at nanosecond precision. Return `REUSE` even when the incoming view
   contains a stronger ID missing from the stored record. The application stores the new evidence on the reused asset.
3. If no strong match qualifies, try continuity and then fuzzy matching, excluding candidates with a strong conflict. An
   absent strong ID is not a conflict. A stronger match still wins over lower-priority differences.

## Continuity matching

Any shared configured continuity value qualifies a compatible candidate. Agent IDs use exact normalized equality; SSH
and TLS compare normalized public keys. Changed values in another continuity type do not veto a match. TLS uses any
shared eligible key: `{A,B}` matches `{A,C}`, `{A}`, or `{A,B,C}`. Order and duplicates do not matter. Certificate
admission and SPKI normalization are unchanged.

- One matching candidate: `REUSE` at `CONTINUITY`, even if weak identifiers differ.
- Several matching candidates: use fuzzy matching only among those candidates.
- No matching candidate: use fuzzy matching among all candidates without a strong conflict.

No continuity or fuzzy decision authorizes merges. Shared keys are not assumed unique and overlaps are not transitive.
The application stores new evidence on a reused key while retaining previous observations under its history policy.

## Fuzzy matching

Compare configured weak types after normalization and deduplication:

- Require at least one shared value.
- Missing types are allowed.
- If both sides supply a non-IP type, they must share a value of that type. This blocks conflicting MACs and names.
- If both sides supply IPs but none matches, require a shared MAC.

Exactly one compatible candidate returns `REUSE`. No match, multiple matches, or no weak evidence returns `CREATE`.
Scores, timestamps, and input order do not resolve ambiguity. Fuzzy decisions always return empty `MergeIndices`.

Weights still calculate the shared-value score using float32 arithmetic in policy order. They do not set a threshold or
select between candidates. Nonfinite scores are errors.

Applications still enforce scanner/network boundaries and supply only active, fresh identifiers. Retire reassigned IPs
from matching while retaining their history separately. An IP-only scan cannot detect reassignment if only the old asset
still lists that IP as active. Repeated ambiguous scans can create additional records.

## Merge plan

These rules apply only after a strong match selects a key. Continuity and fuzzy decisions never merge existing records.

The destination view is the stored selected candidate. Incoming evidence can also link related records. For merge
safeguards, keep the previous ordering: `StrongOrder` followed by `Continuity`. Continuity order affects these existing
merge checks, not continuity selection.

| Evidence                                    | Merge requirement                                                            |
|---------------------------------------------|------------------------------------------------------------------------------|
| Both views have strong or continuity IDs    | Match the source's highest-priority type in the destination or incoming view |
| Either view lacks strong and continuity IDs | Every source weak identifier occurs in the destination's nonempty weak set   |

Check the stored and incoming views separately: partial TLS sets cannot be combined into a match. For example, incoming
Machine X + Agent A can link a stored Machine-X-only key with an Agent-A-only record. A source with a stronger ID
missing from both views cannot join through a weaker ID.

For strong `REUSE`, reject sources that conflict with incoming evidence above the selecting priority, or with the stored
destination at or above that priority. Lower-priority differences may follow a higher match. Weak containment uses only
the stored destination on `REUSE`; an empty source weak set is contained by any nonempty destination weak set.

TLS merge safeguards retain complete-set checks when TLS is the source's deciding type; overlapping sets are not joined
into a synthetic match. A matching higher-priority identity still takes precedence.

Return merge indices in original input order, excluding the selected candidate. `CREATE` returns no merge indices. The
caller preserves earlier evidence and applies the observation and permitted merges atomically.

## Validation

Validate the policy first, then all candidate keys and timestamps, then all identifiers, including unmatched candidates
and types outside the active policy. Reject empty keys (`ErrEmptyCandidateKey`), duplicates
(`ErrDuplicateCandidateKey`), and present timestamps outside UTC years 1–9999. Do not skip candidates or renumber
indices. Policy errors support `errors.Is(err, ErrInvalidMatchPolicy)`; identifier and time errors retain their
categories.

## C API

The public header is [`gvm_asset_identity.h`](../../include/gvm_asset_identity.h). Constructors copy raw values;
`gvm_asset_identity_decide` normalizes them. SSH may include a leading port; TLS may be `x509:<base64-DER-certificate>`.

- Constructors return owned objects; parents own their children. Matching free functions accept NULL.
- `policy_new` creates all three arrays. Fill `continuity` with identifier enum values; clearing an array disables that
  stage. `policy_free` releases all arrays.
- `decide` borrows immutable inputs and returns an owned decision; on failure the decision is NULL. Output slots must
  not alias inputs or each other. Initialize `GError *` to NULL and free it with `g_clear_error`.
- Use real GLib arrays and NUL-terminated strings without embedded NUL bytes. Pointers must reference live, aligned
  objects of the declared types.
- Timestamps contain presence, signed Unix seconds, and nanoseconds (0–999999999), within UTC years 1–9999. Absent
  timestamps have zero seconds/nanoseconds. No Go pointer crosses the ABI.
- Per call: at most 1,048,576 entries per collection, 16 MiB per string, and 64 MiB of private wire arrays/string bytes.
- Errors are `INVALID_INPUT`, `INVALID_POLICY`, or `INTERNAL`. Recoverable Go panics become `INTERNAL`; fatal runtime or
  allocation failures retain normal process behavior.

ABI 3 installs `libgvm_asset_identity.so -> .so.3 -> .so.<version>-<arch>`, the header, and pkg-config metadata. The
added C `continuity` array changes the policy layout. Rebuild consumers against the new header; do not load this library
through an old ABI symlink. The SONAME is independent of the package release version. Consumers need GLib; Go and Cgreen
are build/test dependencies. See the [README](../../README.md#c-build-test-and-install)
for build/install commands. `DESTDIR` stages files without changing metadata; uninstall removes only project files.
CTest uses `CGREEN_NO_FORK=1` for the Go runtime and clears loader overrides. Cross-builds need matching GLib, compiler,
and sysroot.

## Verification

Run `make test`, `make test-install`, `go test -race ./...`, `CGO_ENABLED=0 go test ./...`, and `go vet ./...`.
The [counting matrix](../../identity/counting_matrix_test.go) covers strong/weak combinations, priorities, candidate
ordering, merge plans, and progressive counts. Other Go and C tests cover validation, formats, ownership, and
concurrency.

The historical [C reference fixtures](../../identity/testdata/fuzzy_reference.json) check score arithmetic for
previously selected matches. Their old containment, recency, and merge decisions no longer define fuzzy behavior.
The [issue #11 regressions](../../identity/fuzzy_regression_test.go) cover DHCP, reassignment, ambiguity, and asset
counts.

The [continuity regressions](../../identity/continuity_test.go) cover rotation, partial TLS observations, ambiguity,
strong conflicts, and strong-stage merging. Custom strong-type policies retain their existing exact matching rules.
